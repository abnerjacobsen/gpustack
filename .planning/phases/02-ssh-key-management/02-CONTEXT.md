# Phase 02: SSH Key Management - Context

**Gathered:** 2026-01-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Users can manage EC2 SSH key pairs for AWS GPU instance access — creating new key pairs, importing existing public keys, and cleaning up when no longer needed. This phase implements the `create_ssh_key()` and `delete_ssh_key()` methods of the ProviderClientBase interface for AWS.

**Dependencies:** Phase 1 (AWS client with credentials configured)

**Requirements addressed:**
- SSH-01: System can create new EC2 key pair with generated name
- SSH-02: System can import existing public key as EC2 key pair  
- SSH-03: System returns key pair name for instance creation
- SSH-04: System can delete EC2 key pair by name
</domain>

<decisions>
## Implementation Decisions

### Key generation strategy
- GPUStack generates SSH key pair locally using standard crypto libraries (following ProviderClientBase interface)
- Public key is imported to AWS EC2 via `import_key_pair` API
- Private key is stored securely, never exposed to user
- Support both GPUStack-generated keys AND user-provided public keys (interface accepts `public_key` parameter)
- Key type selection: Claude's discretion (research ED25519 vs RSA 2048/4096 trade-offs)
- Storage approach: Claude's discretion (evaluate GPUStack's existing credential security model)

### Key naming convention
- Auto-generated by GPUStack to ensure uniqueness and naming consistency
- Pattern: `gpustack-{worker-name}-{random-suffix}`
- Suffix format: Claude's discretion (short UUID, timestamp, or random alphanumeric)
- Region inclusion: Claude's discretion (evaluate whether region in name aids debugging or adds noise)

### Private key handling
- Private key never returned to user in API responses
- Store encrypted in database using GPUStack's existing CloudCredential encryption
- Usage pattern: Claude's discretion (evaluate whether GPUStack server needs to SSH to workers)
- Deletion policy: Claude's discretion (evaluate security vs operational needs)

### Existing key conflicts
- Check key pair existence before attempting creation (call `describe_key_pairs` first)
- If key name already exists in AWS: fail with clear error message
- Error message format: Claude's discretion (craft helpful message with fingerprint if useful)
- Orphaned key cleanup: Leave for manual cleanup, no auto-delete on worker failure
</decisions>

</specifics>
